# Как разобрать проект перед интервью

Это учебный проект, подготовленный с AI-помощью. Сначала разберите его и внесите собственное изменение; не представляйте его как рабочую банковскую систему или полностью самостоятельно написанный код.

## Что показать за пять минут

1. README: назовите бизнес-риски — неверные суммы, дубли заявок, чужие данные и сбой сервиса.
2. `tests/ui.spec.ts`: покажите путь «вход → заявка → проверка в UI → проверка через API».
3. `tests/api.spec.ts`: объясните границы сумм и повторную отправку с одним idempotency key.
4. `tests/fixtures.ts`: объясните, зачем каждому тесту свой пользователь и API-контекст.
5. `playwright.config.ts`: покажите запуск тестового сервера, отсутствие retries и диагностику.
6. Запустите отрицательный контроль и объясните, почему команда успешна, хотя внутри один тест намеренно падает.

## Вопросы, на которые нужно отвечать самостоятельно

- Почему денежные значения хранятся целым числом копеек/центов?
- Почему HTTP 200 не доказывает корректность данных?
- Чем UI-тест с проверкой сетевого ответа отличается от отдельного API-теста?
- Зачем setup через API, если проверяем UI?
- Что произойдёт при параллельном запуске без отдельных пользователей?
- Чем ожидание ответа и web-first assertion отличаются от фиксированного sleep?
- Почему retry может скрыть нестабильность?
- Как проверить чужой объект, если его нет в списке другого пользователя?
- Какие проверки остаются за пределами проекта?

## Ваша первая самостоятельная доработка

В `api.spec.ts` добавьте тест: два разных пользователя отправляют одинаковый idempotency key и получают две независимые заявки. Перед запуском объясните ожидаемое поведение. Затем временно уберите user ID из ключа на сервере, убедитесь, что тест обнаружил ошибку, и верните исправный код.

После этого сделайте отдельный commit с объяснением риска и результата. Именно такая доработка поможет обсудить проект предметно, а не только показать сгенерированные файлы.
